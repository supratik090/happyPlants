Indoor Plant Care App

Product scope and technical design for the first Android release. Working title: Hariyali (name not final).

Version 0.4 · Updated 23 October 2026 · Platform: Android · Target minimum: Android 8.0 (API 26)

1. Product vision

A polished, offline-first companion for people caring for indoor, balcony and desk plants. It helps users understand what needs attention today, build a dated record of plant growth, and maintain consistent care habits.

Product promise: users can add plants, log care, see their growth history and use local reminders without creating an account or being online. AI health checks and cloud backup are explicitly deferred until after the first release.

Experience goals

  • From opening the app to logging a care action: ideally under five seconds.
  • Premium, calm, photo-led UI; no generic-looking default screens.
  • Plant care guidance is a starting point, not a rigid schedule. Users can adjust intervals.
  • Never imply an exact or guaranteed diagnosis from a plant photo.
  • All core personal data stays on the device unless the user explicitly exports it, backs it up, or submits a photo for an AI check.

3. Explicitly out of scope for v1

  • User accounts or required sign-in.
  • Cloud sync between devices or a backend database for ordinary plant records.
  • On-device plant diagnosis model.
  • Automatic social media publishing.
  • Complex gamification, streak leaderboards or a single plant-health score.
  • Paid subscriptions or affiliate commerce; the business model remains free with ads only.

4. Navigation and primary flows

Bottom navigation

  • Today: due/overdue care and upcoming tasks.
  • My Plants: photo-led grid/list and plant details.
  • Library: browse/search plants and add one.

Settings are reachable from the Today header. Growth timeline and care history open from the relevant plant detail screen.

First launch → short intro → choose language → add first plant → explain/ask for notifications
Daily use → Today → tap a care action → log saved locally → due date recalculated
Add plant → My Plants → Add → search library or custom plant → edit care schedule → Save
Growth → Plant detail → Add photo → optional observation → dated timeline
AI check → Plant detail → Health check → explain photo upload → choose/capture photo → result → save to history
Data safety → Settings → Export / Import → choose file → validate → confirm → restore

7. Local data model (Room)

Room is the source of truth for user-created records. Avoid a single mutable JSON file as the primary database; it becomes difficult to update individual records, query history and migrate safely. JSON remains useful for the read-only bundled plant library and for user export/import.

EntityKey fields / relationships
Plantid, masterPlantId nullable, nickname, room, addedAt, custom care interval overrides, notes, primaryPhotoPath, archived/deleted state.
CareEventid, plantId, careType, scheduledFor, completedAt nullable, status (done/late/missed/skipped), note. Indexed by plantId and date.
CareScheduleid, plantId, careType, intervalDays or rule, enabled, nextDueAt. Recalculate from events and user overrides; do not rely on a free-running timer.
PlantPhotoid, plantId, filePath, capturedAt, createdAt, caption, photoType (growth/health-check/profile).
Future AI health-check data (later)Do not create or use this table in v1. Add through a Room migration only when AI checks are implemented.
App preferencesStore simple settings in DataStore rather than a Room table unless querying/relating them becomes necessary.

Use stable IDs (UUIDs), foreign keys, indexes for common queries, and Room migrations for every schema change. Store image paths/URIs in Room—not image bytes. Copy photos selected by the user into app-private storage if they need to remain available for a persistent timeline.

8. Plant library data

Bundle approximately 50 species for v1 in assets/plants_master.json, with a schema version. Prioritise common plants found in Indian homes, apartments and balconies. Expand based on search demand in later updates.

Care intervals are suggestions, not guarantees. Pot size, drainage, season, humidity and indoor conditions affect watering. The UI should tell users to check soil/plant conditions and let them adjust intervals. Do not show pet-safety claims unless the source data is reliable and reviewed.

9. Reminder and due-date rules

  • Persist schedules and care events in Room. Calculate due status from the last relevant completed event, interval and user override.
  • Show overdue, due today and upcoming separately; a user-marked “Skip” is not counted as a missed task.
  • Use WorkManager for deferrable maintenance and backup. For user-selected clock-time reminders, select the Android scheduling API based on required precision and current Android restrictions; do not assume WorkManager fires at an exact minute.
  • Handle notification permission on Android 13+ after the user sees value (e.g. after adding a first plant), not as an unexplained first-launch prompt.
  • Test device reboot, timezone change, daylight-saving changes where applicable, app update and denied notification permission.

10. AI health check and privacy

V1 decision: deferred. AI photo health checks are not part of the first public release. No plant photo will be uploaded for AI analysis in v1, and no AI backend or provider key is required.

Revisit after launch as a separate milestone. Before implementation, define an HTTPS backend, explicit photo-consent flow, input validation and resizing, rate limits, provider credential protection, data-retention rules, uncertainty-aware result language, failure handling, and a hard operating budget. Do not put an AI provider secret in the APK or assume ad revenue will cover AI costs.

11. Export, import and backup

  • V1 export creates a versioned archive containing database data and user photos, excluding the bundled plant encyclopedia and transient cache files.
  • Import validates archive format and schema, previews plant/photo counts, and asks before replacing local data. Keep a temporary recovery copy during restore.
  • Show last export/backup date and explain that uninstalling may delete local data.
  • Google Drive backup is a later milestone. When implemented, request the narrowest available Drive scope, document how users revoke access, handle conflicts explicitly and never silently overwrite newer data.

12. Monetisation and analytics

Business model: free app funded by basic ads only; no subscription or affiliate links planned. V1 may use limited, clearly labelled banner/native placements after core usability testing. Ads must not cover controls, interrupt a care action, appear in notifications, or gate reminders, plant records, or core logging. No interstitial or rewarded ads in v1. Before publishing, complete the privacy policy, Google Play Data safety declaration, ad consent requirements where applicable, and disclose third-party data collection accurately. Collect only essential analytics; never send plant photos or personal notes to analytics. The app must remain useful when ads fail to load or the device is offline.

14. Release acceptance checklist

  • New users can add a plant and log its first care action without creating an account.
  • Plant records, care logs and timeline photos persist after closing/restarting the app.
  • Core plant care, search, logging and history work in airplane mode.
  • Care intervals can be changed; overdue, completed and skipped states are understandable.
  • Reminders respect permissions and settings and can be disabled easily; tested on API 26 and a current Android release.
  • Export/import is validated and does not silently destroy existing data.
  • English UI is complete and reviewed; UI text is structured for later Hindi and Marathi localization.
  • Basic labelled ads do not cover controls, interrupt care, appear in notifications or block core features; offline/no-fill states are tested.
  • Privacy policy, Google Play Data safety declarations and ad consent requirements are completed before publishing.
  • All plant images have a recorded source/licence and a fallback placeholder; UI supports accessibility text scaling, contrast, screen readers and varied screen sizes.
  • AI diagnosis, Drive backup, widget, shopping list and growth reels are absent from v1 unless separately approved in a later scope update.
  • App name remains a working title until naming and store/trademark checks are complete.

15. Decisions still required

The first-release decisions below are confirmed:

  • Platform and stack: Android, Kotlin, Jetpack Compose + Material 3, Room, DataStore, MVVM, Hilt, Coroutines/Flow.
  • AI health checks: deferred to a later release; no AI backend or model key in v1.
  • Languages: English at launch; Hindi and Marathi later. Localization foundations are included from the start.
  • Monetisation: free app with basic, unobtrusive ads in v1, added after core UX testing.
  • Offline-first: no required account or backend for core plant-care workflows.
  • Name: intentionally undecided; do not block engineering on naming.
V1 scope is now the implementation baseline. Any additional feature should be treated as a post-launch item unless it is required to meet a listed acceptance criterion.
